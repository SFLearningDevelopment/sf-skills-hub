The operational toolkit this module builds on

This module is about running a cluster day after day — keeping its core components current, seeing what it's doing, upgrading it safely, and fixing it when something breaks. A few operational fundamentals make it click.

Reading a cluster with kubectl

Most operational work starts with a handful of kubectl commands that tell you what the cluster is actually doing:

  • kubectl get — list resources and their high-level status (e.g. get pods, get nodes).
  • kubectl describe — detailed state and events for one resource. The events at the bottom usually explain why something is stuck.
  • kubectl logs — a container's output; --previous shows logs from a crashed prior instance.
  • kubectl get events — recent cluster events, useful for spotting scheduling and resource problems.
Why this matters for this module
Troubleshooting (Section 4) is mostly the disciplined use of these four. A pod stuck Pending or in CrashLoopBackOff almost always explains itself through describe (events) and logs — if you look before you guess.

What "observability" means

Observability is your ability to understand what's happening inside the cluster from the outside, through three kinds of signal:

  • Metrics — numeric measurements over time (CPU, memory, request rates). Often collected by Prometheus and viewed in Grafana, or via CloudWatch Container Insights.
  • Logs — text records from applications and the control plane. Aggregating them (e.g. to CloudWatch) means you can search across the cluster instead of chasing individual pods.
  • Events / audit — Kubernetes events and EKS control-plane logs (API, audit, authenticator) that record what the cluster and its callers did.
Connecting to your other work
If you've built the Prometheus or Grafana skill tracks, this is where they meet EKS — the same monitoring stack instruments your cluster and workloads here.

How problems map to cluster layers

Operational issues usually trace back to one of a few layers of the cluster — and knowing which layer owns a symptom is half the diagnosis:

  • Compute — node capacity and autoscaling: a pod that can't be scheduled often points here.
  • Identity — a workload that suddenly can't reach AWS is often an IAM-role association or an over-tight permission policy.
  • Networking — connectivity problems trace back to pod IP/CNI, network policy, DNS, or load balancer configuration.
  • Core components — DNS and networking add-ons that have drifted out of compatibility can cause cluster-wide symptoms.

So the toolkit here is: kubectl to read the cluster, observability (metrics, logs, control-plane logging) to see it before it breaks, and a mental map of how symptoms point to the layer that owns them. The four sections ahead — add-ons, observability, upgrades, and troubleshooting — turn EKS knowledge into the discipline of running a cluster, not just building one.
