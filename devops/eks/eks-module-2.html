Compute: Node Groups & Fargate
0 of 4 sections complete

The compute foundations this module builds on

In EKS, you own the worker nodes — the machines your pods run on. This module is entirely about those machines: what they are, how AWS can manage them for you, and how their number flexes with demand. A few cloud-compute fundamentals make all of it click.

What a "node" actually is on AWS

A Kubernetes worker node is just a machine that runs your pods. On AWS, that machine is most often an EC2 instance — a virtual server you rent by the second. Each instance has a type (e.g. t3.medium) that fixes its CPU and memory.

Analogy
Think of an EC2 instance as a rented desk in a co-working space. The desk size (instance type) decides how much you can spread out (CPU/memory). Your pods are the people working at the desk. A bigger desk fits more people; renting more desks fits more teams.

Who patches and maintains the machine

An EC2 instance runs an operating system from an AMI (Amazon Machine Image — the template the instance boots from). Like any server, it needs OS patching and updates over time. The central question of this module is who does that work: you, by hand, or AWS, on your behalf.

Why this matters for this module
"Managed node groups" exist precisely so AWS handles the machine's lifecycle — provisioning, AMI updates, graceful replacement — instead of you scripting it. "Fargate" goes further and removes the machine from your view entirely. The whole module is about trading off how much of the node you manage.

Paying for capacity: used vs. idle

You pay for an EC2 instance while it runs, whether or not your pods are using all of it. A node sized for peak load but idle most of the day is capacity you pay for but don't use. Matching capacity to actual demand is the core cost idea here.

Example
A node big enough for your busiest hour sits 80% empty overnight — you still pay for the full node every hour. Scaling down off-peak, or paying per-pod, recovers that waste.

Scaling: more pods vs. more machines

Two different things can "scale" in a cluster, and keeping them straight is essential for this module:

  • Scaling pods — running more copies of your application (more replicas). Handled by the Horizontal Pod Autoscaler (HPA), which adds replicas when load rises.
  • Scaling nodes — adding or removing the underlying machines so those pods have somewhere to run. Handled by a node autoscaler (Cluster Autoscaler or Karpenter).
Example
Traffic spikes → the HPA wants 10 pods instead of 3, but there's no room. The node autoscaler notices the unschedulable pods and adds a node. Traffic falls → pods scale back, the extra node is removed. They work as a pair.

That's the toolkit for this module: nodes are EC2 machines you may or may not manage, you pay for capacity whether idle or used, and pods and nodes scale separately but together. With those in mind, the four sections ahead — managed node groups, Fargate, autoscaling, and choosing a compute model — are really one question asked four ways: how much of the machine do you want to own, and how closely should capacity track demand?
