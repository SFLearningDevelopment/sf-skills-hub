Identity: IRSA & Pod Identity
0 of 4 sections complete

The identity foundations this module builds on

This module is about giving a pod permission to call AWS services — read an S3 bucket, write to DynamoDB — without handing it a static password. To see how that works, you need two ideas side by side: how AWS IAM grants permissions, and what a Kubernetes service account is. IRSA and Pod Identity are bridges between the two.

IAM: users, roles, and policies

AWS IAM (Identity and Access Management) decides who can do what in your AWS account. Three terms matter here:

  • Policy — a document listing allowed (or denied) actions on resources, e.g. "allow s3:GetObject on my-bucket." Permissions are expressed as policies.
  • User — a long-lived identity with its own credentials. Useful for humans; awkward for workloads, because its credentials are long-lived secrets.
  • Role — an identity with policies attached but no permanent credentials. Instead, a trusted party assumes the role and receives temporary, auto-expiring credentials.
Analogy
An IAM user is like your own house key — yours permanently, and a problem if it's copied. A role is like a hotel keycard: issued to whoever is checked in, scoped to certain doors, and it expires on its own. Workloads should use keycards, not house keys.

Temporary credentials and "assuming" a role

The power of a role is AssumeRole: a trusted identity exchanges its own proof-of-identity for short-lived credentials for the role. Those credentials expire automatically, so there's no long-lived secret to leak or rotate. This is the mechanism IRSA and Pod Identity use to get AWS credentials into a pod safely.

Example
Instead of storing an access key in a pod forever, the pod proves who it is and receives credentials that work for, say, an hour — then automatically gets fresh ones. Nothing permanent ever sits in the pod.

Kubernetes service accounts

Inside Kubernetes, a service account is the identity a pod runs as — distinct from human users. By default pods get a service account, and that account can be associated with permissions. Crucially, a pod's service account can carry a projected token proving its identity to outside systems.

Why this matters for this module
IRSA and Pod Identity both work by linking a Kubernetes service account to an IAM role. The pod runs as the service account; the platform exchanges the service account's token for temporary IAM credentials for the linked role. That's the whole trick — service account in, scoped temporary AWS credentials out.

The node role — and why it's too broad

Every worker node has its own IAM role. Without IRSA or Pod Identity, pods can end up using the node's role — meaning every pod on that node shares the same broad permissions. That's the problem this module solves: replacing one shared node-level identity with a scoped identity per workload.

Example
If the node role can read every S3 bucket, then any pod on that node can too — including one that should only touch a single bucket. Per-workload roles fix exactly this.

So the toolkit for this module is: IAM roles carry permissions via policies and are assumed for short-lived credentials; Kubernetes service accounts are the in-cluster identity a pod runs as; and today many pods over-inherit the broad node role. The four sections ahead — why static keys are bad, IRSA, EKS Pod Identity, and least-privilege role design — all answer one question: how do we give each workload exactly the AWS access it needs, with credentials that expire on their own?
