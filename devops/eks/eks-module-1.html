Kubernetes — the fundamentals

Kubernetes is a system that runs your containerised applications across a pool of machines for you. You tell it the desired state ("run three copies of this container, always"), and Kubernetes continuously works to make reality match — restarting things that crash, replacing machines that die, and rescheduling work as needed.

Analogy
Think of Kubernetes as a restaurant manager. You don't tell the manager which cook stands at which station minute by minute — you say "I always want three cooks on the line." If one calls in sick, the manager pulls in another without you noticing. You declare the outcome; the manager maintains it.

The control plane vs. the nodes

Every cluster has two halves. The control plane is the brain — it holds the desired state, makes scheduling decisions, and exposes the API you talk to. The worker nodes are the machines that actually run your containers.

  • Control plane — the API server (the front door you send commands to), the scheduler (decides which node runs what), and etcd (the database that stores the whole cluster's state).
  • Worker nodes — each runs a kubelet (the on-node agent that talks to the control plane) and a container runtime that launches the actual containers.
Why this matters for EKS
This split is the single most important idea for EKS. In EKS, AWS runs the control plane for you — the API server and etcd live in an AWS-managed account, patched and scaled by AWS. You own the worker nodes. Almost everything in this track lives on one side of that line or the other.

The objects you'll meet constantly

Pod

The smallest unit Kubernetes runs — one or more containers that share a network address and lifecycle. You rarely create pods directly; something higher up manages them.

Example
A single web-server container running in a pod, reachable at its own internal IP inside the cluster.

Deployment

A controller that keeps a desired number of identical pods running, and handles rolling updates when you change the image.

Example
"Always keep 3 replicas of web:v2 running." Kill a pod and the Deployment starts a replacement; push web:v3 and it rolls pods over one at a time.

Service

A stable network endpoint in front of a set of pods. Pods come and go with changing IPs; the Service gives them one durable address and load-balances across them.

Example
Your frontend talks to http://orders (a Service) instead of chasing individual order-pod IPs that change every redeploy.

Namespace

A logical partition inside one cluster, used to separate teams or environments.

Example
A staging namespace and a prod namespace sharing one cluster but isolated from each other.

RBAC — who can do what

Kubernetes RBAC (Role-Based Access Control) governs which identities may perform which actions on which resources. A Role is a set of permissions; a RoleBinding grants that Role to a user, group, or service account.

Why this matters for EKS
EKS connects AWS IAM identities to Kubernetes RBAC. When you run a kubectl command, AWS authenticates who you are (IAM), then Kubernetes decides what you're allowed to do (RBAC). Module 1 covers exactly how that mapping is wired — so this RBAC concept is the hook the AWS layer hangs on.

How you talk to a cluster

kubectl is the command-line tool for Kubernetes. It reads a kubeconfig file that tells it which cluster to reach and how to authenticate. Commands are declarative: you usually apply a YAML manifest describing desired state rather than issuing step-by-step imperative orders.

Example
kubectl apply -f deployment.yaml hands Kubernetes a description of what you want; the control plane figures out the steps to get there.

That's the whole foundation EKS builds on: a control plane holding desired state, worker nodes running your pods, Deployments keeping them alive, Services giving them stable addresses, and RBAC governing access. EKS keeps every one of these concepts unchanged — it simply runs the control plane for you and wires AWS IAM, networking, and scaling into the worker side. Everything ahead is "standard Kubernetes, plus the AWS layer." Keep the control-plane / node split in mind and Module 1 will click into place.
