The networking foundations this module builds on

This module covers how traffic moves to and between pods in EKS: how pods get IP addresses, how they reach each other, and how outside users reach your services. Two worlds meet here — the AWS VPC network and Kubernetes networking. A few fundamentals from each make the whole module click.

The VPC: your private network on AWS

A VPC (Virtual Private Cloud) is your isolated network within AWS. It's carved into subnets — ranges of IP addresses, usually split across Availability Zones. Everything you run on AWS gets an IP from a subnet.

  • CIDR block — the IP address range of a VPC or subnet, written like 10.0.0.0/16. A bigger range (smaller number after the slash) holds more addresses.
  • Public vs. private subnets — public subnets can route to the internet; private ones stay internal. Where something sits determines whether it's reachable from outside.
Why this matters for this module
In EKS, pods get real IP addresses from your VPC subnets (via the VPC CNI). That makes pods first-class on the network — and means subnet size directly limits how many pods you can run. Subnet sizing becomes a cluster-capacity decision.

Security groups: stateful firewalls

A security group is a virtual firewall attached to AWS resources, controlling inbound and outbound traffic by rules (port, protocol, source). EKS can even attach security groups to specific pods.

Example
A security group might allow inbound traffic on port 443 from anywhere, but database access only from the application's security group — not the whole internet.

Load balancers: one front door for many pods

A load balancer distributes incoming traffic across multiple backends. AWS offers two that matter here:

  • ALB (Application Load Balancer) — layer 7, understands HTTP/HTTPS, routes by path/host. Ideal for web traffic.
  • NLB (Network Load Balancer) — layer 4, handles raw TCP/UDP at high throughput and low latency. Ideal for non-HTTP or performance-sensitive traffic.
Why this matters for this module
The AWS Load Balancer Controller creates these load balancers automatically from your Kubernetes manifests — an ALB for an Ingress, an NLB for a LoadBalancer Service — instead of you wiring them by hand.

Kubernetes Service and Ingress

From Module 1's refresher: a Service gives a set of pods one stable address. Building on that:

  • Service type ClusterIP — reachable only inside the cluster (the default).
  • Service type LoadBalancer — asks the platform to put an external load balancer (an NLB, via the controller) in front of the Service.
  • Ingress — an HTTP/HTTPS routing layer: rules that map hostnames and paths to Services. With the controller, an Ingress provisions an ALB.
Example
An Ingress rule "shop.example.com/api → orders-service" becomes ALB routing rules that send matching requests to the right pods.

So the toolkit for this module is: pods get VPC IPs (so subnet sizing matters), security groups and network policy govern who may talk to whom, and load balancers driven by Service and Ingress manifests bring outside traffic in. The four sections ahead — the VPC CNI, pod-to-pod policy, the Load Balancer Controller, and secure ingress — all answer one question: how does traffic reach your pods, and how do you keep that path scoped and secure?
